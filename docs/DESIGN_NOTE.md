# Design Note

Setlist Social is for music fans who want a lightweight place to connect artist discovery with their own concert activity. The primary users are concertgoers, playlist explorers, and fans who enjoy seeing what other people are saving or attending. The app solves a small but real problem: music activity is usually spread across ticketing sites, streaming apps, social media, and setlist databases. Setlist Social brings a focused slice of that behavior into one experience where users can search artists, save wishlist artists, record concerts, and watch community activity move in real time.

The domain is Music & Events. I chose Last.fm as the third-party API because it provides public artist search data that fits the discovery workflow without requiring access to a user's private streaming account. Last.fm results are clearly labeled as external data on the Discover page. When a signed-in user saves an artist, the saved wishlist item becomes Setlist Social user-owned data stored in the app database. This separation matters because Last.fm is a public source, while concerts and wishlist items belong to individual users.

The app stores user-owned data for Google-authenticated profiles. A `UserProfile` can own many `Concerts`, many `Reviews`, many `WishlistItems`, and many `ActivityEvents`. An `Artist` can have many `Concerts`. A `Concert` can have many `Reviews`, and it can connect to many `Tags` through a many-to-many relationship. `WishlistItem` connects a user to an artist and can store source metadata such as `Last.fm`. The app also stores public-safe activity records so the community feed can show events such as saved artists and added concerts.

Public frontend routes include `/`, `/about`, `/stats`, `/artists`, `/activity`, and `/discover`. Protected frontend routes include `/dashboard`, `/profile`, `/my-concerts`, `/wishlist`, and `/settings`. The frontend guards protected routes, but the backend is the real security boundary. Backend endpoints under `/api/me` require a signed-in user. If a user is not authenticated, the API returns `401`. If an authenticated user tries to cross a user-owned boundary, such as reading or deleting another user's concert, the backend returns `403`.

Cross-user data access is prevented by looking up the current user's `UserProfile` from the authenticated OAuth subject, then checking ownership before returning or mutating records. For example, `GET /api/me/concerts/{id}`, `PUT /api/me/concerts/{id}`, and `DELETE /api/me/concerts/{id}` verify that the concert's `UserProfileId` matches the current user. Wishlist delete uses the same pattern. Direct backend tests confirm that one signed-in user cannot access another user's records.

The advanced integration is SignalR. I chose it because live activity is a natural fit for a social music app: one browser can add a concert or save an artist, and another browser can see the public activity feed update without refreshing. The SignalR payload is intentionally limited to safe display fields, such as friendly event type, message, display name, timestamp, and optional artist/concert text. It does not broadcast OAuth subjects, emails, private notes, or internal auth identifiers.
